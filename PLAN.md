# Music Remover: расширение Chrome, которое убирает музыку из видео

> **Статус (2026-11-09): MVP готов.** Этапы 0–7 выполнены, расширение работает на YouTube.
> Установка и замеры описаны в [README.md](README.md).
> Принятые решения: модель MDX-Net Kim Vocal 2, ONNX Runtime Web (WebGPU), iframe + Worker,
> строгий режим по умолчанию, time-stretch (WSOLA) для скоростей ≠ 1×.
> Модель идёт в составе расширения, а не скачивается при первом запуске.

## Цель

Пользователь включает расширение, и в видео остаётся только голос (речь), а фоновая музыка вырезается.
Обработка идёт **заранее**: аудио перехватывается в момент, когда плеер буферизует его вперёд,
очищается нейросетью и проигрывается вместо оригинального звука синхронно с видео.

## Границы MVP

| Входит | Не входит (пока) |
|---|---|
| YouTube (обычные видео, десктопный Chrome) | Сервисы с DRM (Netflix, Кинопоиск и т.п.): аудио недоступно |
| macOS на Apple Silicon (WebGPU) | Прямые трансляции |
| Скорость воспроизведения 1x | Мобильные браузеры |
| Режим «строгий»: пока чистого звука нет, тишина | Другие сайты (это этап после MVP) |

## Архитектура

```
 YouTube page (MAIN world)                 Extension (chrome-extension://)
┌──────────────────────────────┐          ┌─────────────────────────────────────┐
│ mse-hook.ts                  │          │ processor iframe (hidden)            │
│  • patch addSourceBuffer     │ segments │  • demux + decode (WebCodecs)        │
│  • patch appendBuffer ───────┼─────────►│  • resample → 44.1 kHz stereo         │
│    (копия аудио-сегментов)   │postMessage│  • Worker: ONNX Runtime Web (WebGPU) │
│                              │(transfer)│    модель разделения → vocals        │
│ player.ts                    │◄─────────┼─ чистые PCM-чанки + таймкоды         │
│  • AudioContext              │  PCM     └─────────────────────────────────────┘
│  • оригинал → Gain(0)        │                       ▲
│  • чистый звук синхронно     │                       │ настройки / статус
│    с video.currentTime       │          ┌────────────┴──────────┐
└──────────────────────────────┘          │ service worker + popup │
          ▲  bridge.ts (ISOLATED world)   └───────────────────────┘
          └── вкл/выкл, настройки
```

### Почему так

- **Перехват на уровне `SourceBuffer.appendBuffer`, а не сети.** YouTube перешёл на свой протокол
  (SABR/UMP), и сетевой формат часто меняется. Но в итоге плеер всё равно кладёт обычные
  контейнерные сегменты (WebM/Opus или MP4/AAC) в MSE. Это самая стабильная точка перехвата.
  Плеер сам буферизует на 30–120 с вперёд, поэтому запас времени на обработку появляется бесплатно.
- **Обработка в скрытом iframe расширения.** У него origin `chrome-extension://`, на него не
  действует CSP YouTube, там можно запускать Worker, WASM и WebGPU. С ним работает `window.postMessage`
  с **transferable** `ArrayBuffer`, то есть без копирования и без JSON-сериализации.
  У `chrome.runtime.sendMessage` сериализация JSON, для мегабайт аудио это плохо.
  Запасной вариант — offscreen document (решаем на этапе 0).
- **Воспроизведение в MAIN world страницы.** У страницы уже есть user activation (видео запущено),
  поэтому AudioContext стартует без проблем, а `video.currentTime` доступен напрямую для синхронизации.

## Модули

### 1. `mse-hook.ts` (MAIN world, `run_at: document_start`)
- Патчить `MediaSource.prototype.addSourceBuffer` и запоминать `mimeType` каждого буфера
  (`audio/webm; codecs="opus"` или `audio/mp4; codecs="mp4a.40.2"`).
- Патчить `SourceBuffer.prototype.appendBuffer`: для аудиобуферов копировать данные
  (`slice()`) и отправлять их дальше, оригинальный вызов не трогать.
- Отличать init-сегмент от медиа-сегментов. Учитывать `timestampOffset`.
- Отслеживать новый `MediaSource` (смена видео, реклама) и сбрасывать состояние.
- SPA-навигация YouTube: событие `yt-navigate-finish`.

### 2. `bridge.ts` (ISOLATED world)
- Вставляет скрытый iframe процессора (`web_accessible_resources`).
- Переправляет сообщения MAIN world ↔ iframe ↔ service worker (настройки, статус).

### 3. Процессор: декодирование
- Демуксинг: `mp4box.js` для MP4, лёгкий EBML-парсер для WebM.
- Декодирование через `AudioDecoder` (WebCodecs). Простой вариант для проверки:
  `decodeAudioData(init + segment)`.
- Таймкоды из контейнера (`baseMediaDecodeTime` / Cluster Timecode) переводятся в медиа-время видео.
- Ресемплинг до частоты модели (обычно 44.1 kHz, стерео).

### 4. Процессор: разделение (Worker)
- ONNX Runtime Web, execution provider **WebGPU** (запасной — WASM SIMD).
- Нарезка на чанки (~8–10 с) с перекрытием (~1 с) и crossfade на стыках.
- Очередь с приоритетом: сначала то, что ближе к текущей позиции воспроизведения.
- После перемотки очередь пересобирается от новой позиции.
- Кандидаты на модель (выбрать по бенчмарку на этапе 0):

  | Модель | Качество | Размер | Скорость | Комментарий |
  |---|---|---|---|---|
  | MDX-Net (vocal, UVR) | высокое | ~30–60 МБ | средняя | 2 дорожки, STFT вне модели |
  | HTDemucs | очень высокое | ~80 МБ+ | медленная | 4 дорожки, тяжёлая для браузера |
  | Open-Unmix (vocals) | среднее | ~30 МБ | быстрая | простая архитектура |

  Целевой показатель: **RTF < 0.5** (на минуту аудио тратится меньше 30 с).
  Проверить лицензии весов (Demucs — MIT, у моделей UVR лицензии разные).

### 5. `player.ts` (MAIN world): воспроизведение и синхронизация
- `createMediaElementSource(video)` → `GainNode(0)`: оригинал заглушен, но UI плеера не трогаем.
  (`createMediaElementSource` вызывается один раз на элемент; YouTube переиспользует `<video>`.)
- Чистые чанки хранятся как `AudioBuffer` в кольцевом кэше по медиа-времени.
- Планирование: чанк с началом `t` запускается в момент
  `ctx.currentTime + (t − video.currentTime) / playbackRate`.
- Коррекция дрейфа: каждые ~250 мс сравниваем позиции; при расхождении > 40 мс перепланируем.
- События: `play`, `pause`, `seeking`/`seeked`, `ratechange`, `waiting`, `emptied`.
- Если чистого звука на текущей позиции ещё нет:
  - **строгий режим** (по умолчанию): тишина и индикатор «обработка…»;
  - **мягкий режим**: временно звучит оригинал.
- Скорость ≠ 1x: в MVP переключаемся в строгий режим (тишина) или ограничиваем скорость;
  позже добавить time-stretch без смены тона.

### 6. Popup и настройки
- Главный переключатель вкл/выкл.
- Статус: модель загружена, сколько секунд обработано вперёд, RTF.
- Режим «строгий / мягкий», выбор модели (быстрее ↔ качественнее).
- Модель скачивается при первом включении, с прогрессом; хранится в Cache Storage / IndexedDB.

**manifest.json (основное):** MV3; `permissions: ["storage", "offscreen"]`;
`host_permissions: ["*://*.youtube.com/*"]`; два content script для одного и того же

`web_accessible_resources` для `processor.html`; CSP с `'wasm-unsafe-eval'`.

## Этапы

### Этап 0. Проверка осуществимости (go / no-go)
1. **Бенчмарк модели**: обычная HTML-страница, ONNX Runtime Web + WebGPU,
   прогнать 60 с аудио из файла через 2–3 модели-кандидата. Замерить RTF и послушать качество.
2. **Перехват на YouTube**: в консоли/userscript пропатчить `appendBuffer`, собрать аудиосегменты
   ролика, склеить и проверить, что они декодируются и звучат правильно.
3. **Транспорт**: убедиться, что iframe расширения на YouTube создаётся и принимает
   transferable-буферы; иначе перейти на offscreen document.

Готово, когда: есть модель с RTF < 0.5 и приемлемым качеством, а сегменты стабильно перехватываются.

### Этап 1. Каркас расширения
- Vite + CRXJS, manifest, popup с переключателем, загрузка расширения в Chrome (unpacked).

### Этап 2. Захват и декодирование
- `mse-hook` → `bridge` → iframe; демукс и декод; лог «получено N секунд аудио вперёд».

### Этап 3. Разделение
- Worker с ONNX, чанкинг с перекрытием, очередь по приоритету, отдача PCM обратно.

### Этап 4. Воспроизведение и синхронизация
- Заглушение оригинала, планирование чанков, обработка перемотки и паузы, коррекция дрейфа.
- Готово, когда: 10-минутный ролик звучит без рассинхрона (> 40 мс) и щелчков на стыках.

### Этап 5. UX
- Статус в popup, индикатор поверх плеера, режимы, загрузка модели с прогрессом.

### Этап 6. Надёжность
- Реклама (смена MediaSource), переходы между видео, Shorts, встроенные плееры (`youtube.com/embed`),
  смена качества, вкладка в фоне, выключение посреди ролика.

### Этап 7. Оптимизация
- fp16/квантизация модели, кэш обработанного аудио по `videoId`, ограничение памяти,
  меньше нагрузки на батарею (не обрабатывать дальше, чем на N минут вперёд).

### После MVP
- Другие сайты без DRM (общий MSE-перехват + обычные `<video src>`).
- Скорость ≠ 1x с time-stretch.
- Опциональный серверный режим (Demucs на GPU) для слабых машин.

## Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Модель медленнее реального времени | средняя | Этап 0; лёгкая модель; fp16; обработка на сервере как запасной вариант |
| Остатки музыки и артефакты, особенно вокал в песнях | высокая | Честно описать ограничение; выбор модели; строгий режим |
| YouTube меняет плеер и ломает перехват | средняя | Хук на `appendBuffer` (стандартный API), а не на сеть; быстрые обновления |
| Рассинхрон звука и видео | средняя | Перепланирование по `currentTime`, тесты логики синхронизации |
| Большой размер модели | высокая | Скачивание при первом включении, кэш, выбор модели |
| Правила YouTube / Chrome Web Store | низкая–средняя | Только локальная обработка, ничего не скачивается и не сохраняется как файл |
